# KR32OS M0-M4 Implementation Plan

Status: **ready for implementation; M0 may start.**

Baseline: `9ec94bb` (`kr32os: decide directory shell and display details`).

This plan implements KR32OS milestones M0 through M4 only. M5 and later
(scheduler, multicore, writable filesystem, user shell) remain out of scope.

## 0. Readiness answer

- **M0 and M1:** ready to implement.
- **M2:** design is ready, but requires host-side serial-device and UI-input
  work first.
- **M3:** ready after M1; requires the OS boot path to attach a DeviceBus.
- **M4:** implementable, with two integration prerequisites that this plan
  resolves explicitly:
  1. the loader discovers the embedded initrd location from a verified
     `kernel.meta` sidecar;
  2. the kernel uses a saved-kernel-context trampoline to return from the init
     process because the scheduler does not exist until M5.

No remaining architecture decision blocks M0-M4. The five review points have
been decided: sidecar metadata, form-feed clear, assembly trampoline, M0-first
ordering, and a 10,000-instruction virtual timer tick.

## 4. Host prerequisites

These are shared by M1-M4 and must be implemented in order.

### H1 — BootInfo and OS metadata

- Define the fixed BootInfo page ABI at `0x0003_F000`.
- Add magic `K32B`, version, struct size, memory ranges, kernel range,
  framebuffer fields, and initrd fields.
- `kr32 os` writes BootInfo before reset and places its address in `R2`.
- Add `kernel.meta`, a sibling sidecar generated by the OS build:

  ```text
  magic        "K32M"
  version      1
  entry
  initrd_offset
  initrd_size
  checksum     CRC32 over the kernel image
  ```

  The loader reads it when present and fills the BootInfo initrd fields. When an
  initrd is embedded, a missing or invalid sidecar is an error rather than a
  silent no-initrd boot. A checksum catches a stale sidecar paired with a newer
  kernel. `--meta <path>` can override the sibling path for development. This
  keeps the flat kernel header-free for M0-M4; self-contained packaging is
  revisited later.
- The GUI `load_os` path must create the same BootInfo page.
- Tests: valid/invalid magic, version, size, checksum mismatch, and
  out-of-range fields.

### H2 — DeviceBus for OS boots

- Attach a `DeviceBus` to the machine in `kr32 os` mode and in
  `DebuggerUI`/`Session` OS mode.
- Keep the host syscall handler for the temporary debug console, but do not use
  host vectors as OS ABI.
- Ensure timer and serial MMIO are reachable before M2/M3.

### H3 — Serial device and UI input

- Add `SerialDevice` at `0xFFF0_5000`:

  | Offset | Register |
  | --- | --- |
  | `0x00` | data: read consumes RX, write transmits TX |
  | `0x04` | status: RX-ready, TX-ready, overrun |
  | `0x08` | peek: next RX byte, `0xFFFFFFFF` empty |

- 4 KiB RX FIFO; drop new bytes when full and set overrun.
- Expose test helpers to enqueue input and drain TX.
- UI console:
  - capture text keys only while the pointer is over the console panel;
  - Enter sends LF, Backspace sends DEL;
  - Ctrl-V pastes normalized clipboard text;
  - other Ctrl combinations send their control byte;
  - F-keys remain debugger shortcuts.
- Add a `control` flag to the platform key event and pass it through.
- Add a test input path (CLI `--serial-input` or equivalent) so CTest can drive
  the OS shell deterministically.
- `clear` emits form feed (`0x0C`) in M2; the UI serial console clears its
  displayed text on form feed. ANSI terminal parsing is deferred until a later
  console milestone.

### H4 — User build and initrd

- Build user programs with `kr32 cc -S`, the OS `crt0.S`, and `syscall.S`.
- Link the user image flat at `0x0040_0000`.
- `mkinitrd` creates the `K32I` archive:
  - magic `K32I`, version 1;
  - at most 64 entries;
  - 32-byte names, offset, size, entry.
- Generate `initrd.S` with `.byte` records and link it into kernel `.rodata`.
- Generate `kernel.meta` from the linker map/symbols.
- Do not add `.incbin` to the assembler.

### M4 — memory, initrd, first user process

Tasks:

- [x] Implement bitmap physical-page allocator; reserve low 4 MiB and the
      identity-mapped user-stack window.
- [x] Implement bump `kmalloc`/`kfree` over the kernel heap.
- [x] Allocate user code frames from the bitmap and map them RX.
- [x] Build user address space at `0x0040_0000`.
- [x] Map user stack top `0x07F0_0000` with guard `0x07E0_0000`.
- [x] Enforce W^X page permissions.
- [x] Implement `crt0.S`, syscall wrappers, and minimal user `init`.
- [x] Generate and embed the `K32I` initrd.
- [x] Generate/read `kernel.meta`.
- [x] Generate CRC-checked `.sym` sidecars and optional `.k32` images for

- [x] Implement process table (256 entries), PID allocation, zombie exit.
- [x] Implement syscalls: exit, write, read, yield, getpid, brk.
- [x] Implement fds 0/1/2 connected to serial.
- [x] Implement the minimal synchronous user-return trampoline:
      - assembly saves the shell's kernel SP/PC and callee-saved state;
      - `IRET` enters user mode;
      - the exit syscall restores the saved kernel context;
      - no timer preemption or scheduler is involved.
- [x] Boot: spawn init, wait for exit, reap, continue to kernel shell.
- [x] Implement shell `ls`, `cat`, `run`.
- [x] Add user-mode tests: banner output, exit status, fault kills process,

- [x] Run gates, log, and commit M4.

```text

```

Out of scope for M4:

- fork/exec
- scheduler/context switch
- COW
- writable filesystem
- user shell
- framebuffer console
- multicore

M4 deferred follow-ups:

- `brk` currently returns the existing break without growing user data pages;
- the process-table-full `-EAGAIN` regression test is not yet automated;
- user code frames are allocated from the bitmap, but the initial user stack
  still uses a fixed identity-mapped physical window.

## 8. Approved starting decisions

The five review points are approved:

1. `kernel.meta` sidecar with CRC32, required when an initrd is embedded.
2. Form-feed (`0x0C`) clear in M2; ANSI handling deferred.
3. Saved-kernel-context trampoline for M4; no scheduler until M5.
4. Start M0 now; implement H1-H4 in dependency order.
5. Virtual timer with a 10,000-instruction reload; not wall-clock time.

Implementation begins with M0. Any newly discovered ABI conflict pauses the
milestone and is recorded in `implementation.md` before proceeding.
